# Автообновление распакованной установки по клику — дизайн

- Дата: 2026-11-06
- Статус: принят пользователем, готов к плану реализации
- Версия продукта после реализации: 2.3.0
- Предыстория: кнопка «Проверить обновления» появилась в 2.2.0 (коммит `ccebb1a`) и
  умела только назвать новую версию и отдать команду пересборки. Этот спек заменяет
  команду настоящим обновлением.

## 1. Задача и рамка

Расширение устанавливается как распакованное (`chrome://extensions` → «Загрузить
распакованное»), из папки `dzen-rewriter`. Такой установке Chrome не разрешает
перезаписывать свои файлы, а `chrome.runtime.requestUpdateCheck()` работает только с
магазинными установками. Значит «обновить по клику» возможно ровно в одном смысле:
клик должен **записать новые файлы в папку установки** и **перечитать их**.

Что считается успехом: после клика человек не набирает в терминале ничего. Единственное
действие, которое он делает руками, — один раз выбирает папку в системном диалоге.

Что вне задачи: публикация в Chrome Web Store (там обновление делает сам Chrome, но
нужен аккаунт за $5, модерация и переустановка из магазина); native messaging-хелпер
(потребовал бы ставить бинарь и править реестр, то есть хуже команды); обновление
установки, у которой папку удалили или перенесли.

## 2. Что измерено, а что принято на веру

Зонд `.agent/tmp/probe-autoupdate.cjs` на стабильном Chrome 156 (расширение, загруженное
через `Extensions.loadUnpacked`, страница `chrome-extension://<id>/popup.html`):

- `window.showDirectoryPicker` — `function`, `window.FileSystemDirectoryHandle` —
  `function`, `window.isSecureContext` — `true`. То есть API выбора папки на странице
  расширения есть.
- Доверенный клик (`Input.dispatchMouseEvent`) по кнопке поднимает системный диалог:
  обещание `showDirectoryPicker({mode:"readwrite"})` осталось незавершённым, ошибки не
  было. Не-доверенный `.click()` для этого не годится, и это тот же капкан жеста, что
  уже закрыт для `chrome.permissions.request`.
- IndexedDB на странице расширения открывается — рукоять папки есть где хранить.

Файлы загруженного расширения перезаписываются — это подтверждено не зондом, а самой
практикой проекта: `node tools/build-extension.cjs` каждый раз пишет в ту же папку
`dzen-rewriter`, из которой расширение загружено, и сборка проходила при установленном
расширении. Windows эти файлы не держит.

Не измерено и остаётся риском: перечитывает ли `chrome.runtime.reload()` файлы с диска у
настоящей распакованной установки. На расширении, загруженном через CDP, он ведёт себя
иначе — выгружает навсегда (проверено ранее, см. комментарий в `test/paths.cjs`), поэтому
CDP-зонд ответа не даёт, а трогать рабочую установку ради ответа нельзя. Дизайн построен
так, что этот исход покрыт явно (исход B в разделе 5) и всё равно лучше сегодняшнего дня.

## 3. Состав файлов, которые пишются

Список не зашивается в код, а выводится из далёкого `manifest.json` — иначе обновление
не смогло бы принести новый файл:

1. из манифеста: `background.service_worker`, каждый элемент `content_scripts[].js` и
   `content_scripts[].css`, `action.default_popup`, `options_ui.page`, все значения
   `icons` и `action.default_icon`;
2. из каждого найденного на шаге 1 HTML: атрибут `src` у `<script>` и `href` у
   `<link rel="stylesheet">`. Второй уровень не обходим: все страницы перечислены в
   манифесте. Так в набор попадает `popup.js`, которого в манифеста нет.

Путь принимается только относительный: без ведущего `/`, без буквы диска, без сегмента
`..`, без `\\`, без `#` и `?`. Всё остальное отбрасывается с явным списком причин в
статусе. Файлы, которых в новом наборе нет, не удаляются — они остаются на диске мёртвым
грузом; это принято осознанно, удаление чужих файлов из папки опаснее мусора.

Каждый файл грузится с тем же префиксом, что и `UPDATE_MANIFEST_URL`, то есть
`https://raw.githubusercontent.com/zanzibara82/dzen-up/main/src/extension-src/<путь>`.
Новых доменов не появляется, право `https://raw.githubusercontent.com/*` уже спрашивается
с 2.2.0. Манифест прав на расширение не меняется совсем: File System Access API не требует
ничего в `manifest.json`.

Сырой ответ ограничен `API_MAX_BYTES`, как и остальной сеть-код продукта.

## 4. Как идёт запись

1. Прочитать далёкий манифест, посчитать состав, скачать **все** файлы и проверить, что
   каждый получился: 404, не-JSON там, где JSON, пустое тело или обрезанный ответ
   означают «не пишем ничего» (исход F).
2. Завести журнал: `chrome.storage.local.dzrUpdateIntent = {from, to, at}`.3. Старые байты затрагиваемых файлов скопировать в `.dzr-backup/<from>/` внутри папки
   установки. Нужен именно диск: откат должен пережить убийство браузера, а в памяти он
   его не переживёт. Chrome лишние файлы в распакованной установке игнорирует.
4. По каждому файлу: прочитать локальный байт в байт, сравнить с далёким, совпал — не
   трогать. Пишем через `getFileHandle(..., {create:true})` + `createWritable()`; для
   `icons/` предварительно `getDirectoryHandle("icons", {create:true})`.
5. `manifest.json` — последним.
6. Отметить в журнале `written: true` и вызвать `chrome.runtime.reload()`. Попап при
   этом умирает, и это нормально.

Флаг `written` нужен ровно для одного различия, и без него раздел 5 не работает: журнал
**без** него означает «письмо не закончилось» (исход D — «Дописать» и «Вернуть»), журнал
**с** ним при старой версии в памяти означает «на диске всё новое, браузер не перечитал»
(исход B — одна подсказка про ⟳, кнопок не надо).

Повтор клика идемпотентен по построению: шаг сверки байтами допишет ровно то, что не
дописалось. Это снимает потребность диагностировать полусостояние файлом к файлу — его
достаточно заметить и предложить два действия (раздел 5).

Откат при ошибке на шаге 4: все уже записанные файлы возвращаются из сохранённых в
памяти байтов, журнал помечается прерванным, человек видит причину.

## 5. Кнопки, состояния и шесть исходов

Разметка в попапе: «Проверить обновления» остаётся как есть и работает без папки. На
находке новой версии рядом появляется «Обновить сейчас»; «Скопировать команду обновления»
остаётся запасным путём всегда. На незавершённом журнале вместо них — «Дописать» и
«Вернуть <прежнюю версию>». Статус обязан называть папку, в которую пишем, и обе версии
числом. Право на папку запрашивается **синхронно, до первого `await`** в обработчике клика.

Журнал снимается только тогда, когда следующий открытый попап увидел на диске обещанную
версию. Любое открытие попапа, заставшее журнал, знает: прошлое обновление не завершилось.

| исход | что видит человек | чем лучше сегодняшнего дня |
|---|---|---|
| A. записал и перезагрузил | «✅ Обновлено до 2.3.0» при следующем открытии | набирать команду в терминале не надо |
| B. записал, `reload()` не перечитал | «⚠️ Файлы обновлены, браузер их не перечитал — нажмите ⟳» | было: `git pull` + сборка + ⟳ |
| C. не начал писать (нет права, отказ, папка не та) | статус с причиной; команда-резерв на месте | то же самое, но причина названа словами |
| D. оборвалось на середине | «Обновление не завершено: на диске 2.2.0, ждали 2.3.0» + «Дописать» + «Вернуть 2.2.0» | продолжения не было вообще |
| E. папку удалили, перенесли или доступ отозвали | «Папки с исходниками на месте нет» + команда-резерв | команда падает в терминале без объяснений |
| F. далёкий манифест ссылается на отсутствующий файл | файл не найден до первой записи, не пишем ничего | `git pull` тоже упадёт, но после правки рабочего дерева |

Худший реальный исход — D, и у него есть выход в один клик в обе стороны. Полностью
атомарной записи файлов средствами Chrome нет, и дизайном это не снимается.

## 6. Выбор папки и его проверка

Диалог `showDirectoryPicker({mode:"readwrite"})` делается один раз на установку. Рукоять
хранится в IndexedDB (имя базы и ключ фиксируются в коде и в тесте). При каждом обновлении
рукоять читается обратно, право проверяется `queryPermission({mode:"readwrite"})` и при
необходимости запрашивается `requestPermission`.

Выбор проверяется до любой записи: в папке должен лежать `manifest.json` с
`manifest_version: 3` и `name`, равным `chrome.runtime.getManifest().name`. Не совпало —
«это не папка расширения», ни один файл не тронут.

Настройки и API-ключ при обновлении не задействованы: они живут в `chrome.storage` внутри
профиля браузера, а не в папке установки, и обновление их ни читает, ни пишет.

## 7. Безопасность

Канал тот же, что у `git pull`: HTTPS, тот самый репозиторий, чей адрес уже зашит в
`UPDATE_MANIFEST_URL`, и ничего больше. Пути фильтруются (раздел 3), новые домены не
появляются, чужие файлы не удаляются. Оговорка, которую нужно помнить: это канал
самообновления кода. Для личной распакованной сборки это осознанный размен, а для
магазина — причина отказа; публикация в магазин (раздел 1) эту ветку закрывает.

## 8. Тесты

Логика делится так, чтобы всё, кроме самого диалога, проверялось.

- **Новый файл `update.js`**, грузится в попапе перед `popup.js`. В нём — чистые функции:
  `updateFileSet(manifestObj, htmlTexts)` → состав файлов, `isSafeRelPath(p)` → фильтр
  путей, `planUpdate(localBytesMap, remoteBytesMap)` → что менять и в каком порядке
  (манифест последним). Они же экспортируются на `globalThis`, чтобы их читал юнит-набор.
  Отдельный файл, а не толстый popup.js: popup.js весит 39 КБ и тестовать его целиком
  тяжело, а `update.js` грузится в Node тем же приёмом, что `test-reliability.cjs`
  грузит `background.js` (`new Function`).
- **Юнит-набор** (`test-reliability.cjs`, новый раздел): состав файлов из реального
  манифеста и реального `popup.html` равен содержимому собранной папки без README;
  фильтр путей отвергает `/x`, `..`, `a/../../b`, `C:\x`, `a?b`, `a#b`; план не пишет
  совпавшие файлы и ставит `manifest.json` последним.
- **Браузерный набор** (`test-popup.cjs`): весь путь с подставной рукоятью. Наш код зовёт
  только `getDirectoryHandle`, `getFileHandle`, `createWritable`, `queryPermission`,
  `requestPermission`, а это обычный объект, который тест собирает сам. Проверяются:
  запись всех файлов и их байты, порядок (манифест последним), откат после 404, журнал до
  первой записи и его снятие, состояние D с двумя кнопками, откат из `.dzr-backup/`,
  отказ в праве, «это не папка расширения», и что при любом исходе `chrome.storage` с
  настройками и ключом не тронут.
- **Сторожа** (`test-docs.cjs`): состав файлов выводится из манифеста, а не из списка в
  коде; адрес далёкого манифеста, домен права и `update.js` не разъехались; README
  описывает «Обновить сейчас» и не обещает то, чего код не делает.
- **Живой клик** — единственный шаг, который автоматизацией не проверяется: один
  настоящий выбор папки в вашей установке. Он входит в приёмку, а не в прогон.

## 9. Критерии приёмки

1. Юнит-набор, браузерный набор и сторожа зелёные; полная регрессия 22 наборов зелёная.
2. В собранной папке `update.js` лежит, `popup.html` его подключает до `popup.js`,
   состав файлов обновления совпадает с реальным набором файлов пакета.
3. Версия 2.3.0 в четырёх местах: `src/extension-src/manifest.json`, `package.json`,
   бейдж в `popup.html`, строка в README.
4. На живой установке: «Проверить обновления» → «Обновить сейчас» → выбор
   `dzen-rewriter` → файлы на диске совпали с `main`, без единой напечатанной команды.
5. Исход B проверен на живой установке и задокументирован фактическим текстом статуса:
   либо «обновлено», либо «нажмите ⟳».
6. Ни один ключ, лог и проверка не содержат значения `aiKey`.
