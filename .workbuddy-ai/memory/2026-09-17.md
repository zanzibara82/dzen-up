### Главная находка: проверка проходила по неверной причине

Первый вариант искал `/лимит\s+(\d+)\s*КБ/` по всему файлу и находил **комментарий**
(строка 79: «узнали про лимит 8 КБ»), а не сообщение об ошибке (строка 142). Подменил
цифру в сообщении на 16 — проверка этого не заметила и осталась зелёной.

Это худший вид теста: он «проходит», ничего не проверяя. Починил якорем на фразу, которую
видит пользователь: `/слишком большое для синхронизации\s*\(лимит\s+(\d+)\s*КБ/`. Теперь
подмена даёт 2 провала («та же цифра в README», «та же цифра в подсказке попапа»).

Заодно укрепил остальные извлечения от той же ловушки — **комментарий это не код**:

Проверил grep-ом, что закомментированных объявлений и полей сейчас нет, — то есть проверки

## Ложная тревога: баг с явным `.xml` не подтвердился (и это важно)

Заподозрил настоящий баг. Право на карту сайта строится как `site + "/*"` — и в попапе
(`siteOrigins`), и в фоне (`buildLinks`). А README разрешает указать карту файлом явно:
`https://auto-dom24.ru/my-sitemap.xml`. Тогда шаблон выходит `https://auto-dom24.ru/my-sitemap.xml/*`,
и по рассуждению он **не покрывает сам файл** — значит документированный сценарий молча
не работает, а человек получает «Нет доступа к сайтам из списка» без шанса это исправить.

Рассуждение выглядело убедительно, и соблазн доложить было сильным. Проверил.

1. **Опыт №1** (`.workbuddy-ai/tmp/probe-pattern.cjs`, удалён): у расширения есть широкое
   право `dzen.ru/*`, спрашиваю `permissions.contains` про разные шаблоны. Всё `true` —
   широкое право покрывает что угодно, опыт **бессмысленен**.
2. **Опыт №2** (`probe-pattern2.cjs`): отдельное минимальное расширение ровно с узким правом
   `http://127.0.0.1:8791/my-sitemap.xml/*` плюс локальный сервер **без заголовков CORS**
   (иначе успешный `fetch` ничего не доказывал бы). Ответ: `contains` = true, `fetch` = 200.
   Выглядело как подтверждение бага.
3. **Контроль** — то же самое, но право заведомо не покрывает адрес (`/other/*`). Ответ
   **ровно такой же**: `true` и `200`.

Вывод: измерялся не тот механизм. `permissions.contains` оказался похостовым (шаблон пути
не уточняет ответ), а `fetch` из service worker в этом окружении вообще не был заблокирован
CORS. Гипотеза **не подтверждена и не опровергнута** — этим опытом её просто нельзя проверить.
Докладывать «нашёл баг» было бы враньём, поэтому не докладываю.

Что проверяемо и в порядке: сам выбор адреса карты покрыт юнит-тестом —
`test-links.cjs:197` «sitemap: явный .xml берётся как есть» →
`sitemapCandidates("https://a.ru/my.xml") === ["https://a.ru/my.xml"]`. То есть нужный файл
действительно запрашивается; вопрос остался только про гранулярность права в Chrome.

**Приём на будущее: контроль обязателен.** Прежде чем говорить «нашёл баг», прогони опыт,
в котором результат обязан быть отрицательным. Если и там «всё хорошо» — инструмент не
измеряет ничего, и предыдущие «подтверждения» пусты тоже. Дешёвый контроль — инвертировать
условие и убедиться, что ответ меняется.

## Запрос на доработку: кнопка «Подобрать картинки» (обсуждение)

Алексей спросил, можно ли добавить в панель кнопку, которая подбирает картинки из поиска
Яндекса и Гугла по заголовку и смыслу статьи. Разобрал источники — вывод неочевидный,
поэтому записываю факты, чтобы не искать заново.

**Яндекс — официальный API есть.** Yandex Search API (AI Studio), поиск изображений по
текстовому описанию:

```
POST https://searchapi.api.cloud.yandex.net/v2/image/search
Authorization: Api-Key <ключ>
{ "query": { "searchType": "ru", "queryText": "...", "page": "0", "familyMode": "strict" },
  "imageSpec": { "format": "jpeg", "size": "LARGE", "orientation": "horizontal" },
  "docsOnPage": "5", "folderId": "<каталог>" }
```

Ответ — JSON, в поле `rawData` лежит **XML в base64**. Нужен кабинет Yandex Cloud: каталог,
сервисный аккаунт с ролью `search-api.webSearch.user`, API-ключ с областью
`yc.search-api.execute`, платный счёт. `docsOnPage` — до 60, `imageSpec.size: LARGE` —
от 800×600. Разбирать XML регуляркой: в service worker нет DOMParser, а для sitemap у нас
уже так сделано.

**Гугл — официально нельзя.** Custom Search JSON API **закрыт для новых клиентов**,
действующих обязали мигрировать до **1 января 2027** (100 запросов/сутки бесплатно,
$5/1000 сверх, до 10 000/сутки — но новым не подключиться). Скрапинг Google Картинок —
CORS, антибот, нарушение ToS, развалится при смене разметки. Альтернатива — платные
агрегаторы выдачи (скрапинг как услуга) либо фотостоки.

**Фотостоки как замена:** Pexels, Pixabay, Unsplash — официальный API, бесплатно,
лицензия на использование. Для публикации в своём канале это ещё и вопрос прав: картинка
из выдачи чужая, у неё есть автор.

**Главный технический риск — не поиск, а вставка.** Сохранять картинки при переводе мы
умеем (`buildVoidClone`), но *создать* новую в редакторе Дзена — другое дело: ProseMirror
может не принять внешний `<img src>`, а Дзен обычно требует свою загрузку. Плюс hotlink на
чужой сайт ненадёжен. До обещаний нужен опыт: вставить картинку и посмотреть, что выживет.

Развилку по источнику оставил за Алексеем (Яндекс / Яндекс+фотосток / Яндекс+агрегатор).

# Подбор картинок: источник выбран — только Яндекс, только горизонтальные

Алексей решил развилку: **только Яндекс, только горизонтальные картинки.** Google
отпадает сам (Custom Search закрыт для новых), фотостоки — тоже.

## Что выяснилось по API

Горизонтальность **фильтрует сам поиск** — `imageSpec.orientation`. Это снимает нужду
парсить ширину с высотой: вертикальные просто не приходят. Размеры из XML всё равно
читаем и фильтруем ещё раз, если они есть.

**Форма enum описана в двух местах по-разному**: справочник API даёт
`IMAGE_ORIENTATION_HORIZONTAL`, а рабочий пример запроса — `horizontal`. Без ключа не
проверить, поэтому первая попытка идёт полной формой, а на 400 — короткой. 400 не
расходует квоту, так что запасной путь почти бесплатен.

`fetchJson` терял тело ответа на 4xx — добавил опцию `errorBody`. Без неё пользователь
видел бы «HTTP 400» без причины, а Яндекс как раз объясняет причину словами.

## Вставка оказалась уже решённой

Главный риск («ProseMirror не примет внешний `<img src>`») снялся чтением кода: замена
текста давно идёт через настоящий `ClipboardEvent("paste")` с `text/html` — редактор сам
строит свои узлы. `cleanAttrs` при этом вырезает только `data-pm*`/`on*`/`contenteditable`,
то есть `src` не трогает. Значит и наш круговой рейс, и вставка картинку несут.
Успех определяю не по факту вызова, а по документу: после вставки ищу узел с этим
адресом в редакторе (`imageInEditor`). Не нашёл — отдаю адрес в уведомлении.

## Найдено и починено по ходу

**Заголовок статьи брался не тот.** `articleTitle` смотрел только внутри найденного
редактора, а на Дзене заголовок — отдельное поле над телом. Тест поймал это сразу:

внутри редактора → первый непустой блок.

(`topBlocks`), а не по символам, и **не зависит от каретки**. Заголовки пропускаются

лестницы, а счёт — по документу: `countOurImages` считает узлы с нашими адресами, поэтому
удалённая картинка освобождает место, а вставленная дважды занимает два. На моке вышло
[0, 3, 6, 9] из 10 блоков — ровно как просили.

## Chrome и contenteditable: обёртку не удержать

Позиция «перед блоком» для Chrome — позиция ВНУТРИ блока: `<p><img></p>` он превращает
в строчку внутри соседнего узла и вешает на картинку его inline-стили
(`<h2><img style="font-size:16px">Что изменилось</h2>`). Пробовал смещение среди детей
редактора и `insertParagraph` перед вставкой — первый вариант ничего не изменил, второй
оставил мусор (`<h2><br></h2>`). Поэтому позиция честно называется «перед блоком», форма
узла — дело редактора, а успех по-прежнему проверяется по документу. В README это сказано
прямо, без обещания «отдельного блока».

Заодно нашлась настоящая поломка окна: оно мерилось пустым, а плитки растягивали его за
край экрана — второй ряд был недоступен для клика. Лечится перестановкой окна после смены
содержимого; тест теперь сторожит геометрию (`panelBox`) и краснеет, если перестановку убрать.

## Уборка копий за прогоном (и предел песочницы)

Причина роста `tmp` найдена точно: каждый набор делает свою копию расширения
(`copyDir(SRC_EXT, TEST_EXT)` в `PATHS.SCRATCH`) и не убирает за собой. За четыре дня — 756 папок,
311 МБ; за один прогон добавляется ~18 копий и ~7 МБ (проверено: 774 → 792 после прогона).

Сделал уборку на уровне прогона — `test/clean-scratch.cjs`, вызывается из `run-suite.sh` **только
при нуле провалов**: список копий снимается до прогона и на stdin уходит в скрипт, который убирает
лишь то, что появилось сейчас. При провалах копии остаются — по ним разбирают, что грузилось в
Chrome (так и было задумано). Внутри скрипта — проверка каждого пути: удаляем только внутри
`.workbuddy-ai/tmp` и только имена с `test-ext-`.

Проверил в обе стороны, как и положено: новая копия убирается, копия из списка «до» остаётся,
посторонние папки (`ext-uniqurl`, `chrome-profile`) не трогаются.

**Но в песочнице уборка не проходит:** `SAFE_DELETE_BULK_CONFIRM_REQUIRED`, порог ~50 элементов
за ход. 18 копий × ~15 файлов — сильно больше, поэтому после прогона копии остаются. Сообщение
скрипта переписал так, чтобы это не выглядело поломкой: он прямо говорит, сколько копий песочница
не дала убрать и что они уйдут при запуске в обычном терминале. Накопленные 792 копии не трогал —
хозяин выбрал их не удалять.

Заодно уточнение по среде: в консольном инструменте Windows заблокированы `Add-Type` и COM — то
есть штатной корзины нет вовсе. Это записано в MEMORY.md («Приёмы»).

## Мусор в tmp: причина устранена, а не подметена

Первая попытка (уборка после прогона) оказалась лечением симптома — и, что хуже, вошла в
противоречие со второй. Настоящая причина: имена копий расширения содержали `pid` и `Date.now()`,
поэтому каждый набор каждый раз создавал НОВУЮ папку. За четыре дня — 756 штук, 311 МБ.

Что сделано: имена копий стали постоянными — `test-ext-<набор>` (14 тестов + `scratchExt` в
`paths.cjs`). Прогон перезаписывает те же папки, мусор не появляется вообще. Уникальность
осталась там, где она нужна, — у профилей Chrome: они в системной temp, и два одновременных
прогона не должны делить профиль.

Почему подмена файлов в копии не залипает между прогонами: `copyDir` идёт ПЕРЕД патчем
(`YANDEX_IMAGE_API` в `test-images-ui.cjs`, `CHANNEL_API` в `test-linkify.cjs`), значит перезапись
возвращает исходный файл, и строка для замены снова находится. Проверено двойным прогоном обоих
патчащих наборов: `test-images-ui` 73/0 дважды, `test-linkify` 47/0 дважды — на второй раз падения
«не нашёл строку» нет.

Уборку `clean-scratch.cjs` после этого удалил: с постоянными именами она удаляла ровно те папки,
которые теперь переиспользуются (в прогоне убрала 4 и пыталась убрать ещё 5). Код, который делает
бессмысленное, лучше убрать, чем держать «на всякий случай».

Проверка результата: три набора подряд (storage 31, popup 86, format 24) — копий до 799 и после
799, ни одной новой. Полный прогон — 932 проверки, 0 провалов, 21 набор.

Накопленные 799 папок (~330 МБ) остались: хозяин выбрал их не удалять. Если решит — удалю разом,
песочница попросит подтверждение на массовое удаление.

## Мусор в temp: 832 профиля → 14

Причина устранена раньше (постоянные имена + `freshProfile`), здесь — уборка накопленного. Хозяин
почистил temp сам, осталось 26 папок: 14 постоянных и 12 старых.

**Что выяснилось про удаление в этой среде** (прежняя запись «корзины нет» — неверна):

- `rm` из консольного инструмента идёт **не напрямую**: обёртка safe-delete отправляет файл в корзину

- Если корзина не сработала, удаление **не выполняется** (`SAFE_DELETE_FAIL_CLOSED`) — файл остаётся

- 11 папок не удаляются вовсе: `EPERM` на каждый файл внутри `Default`, причём **и без песочницы**.

  из 1092. Значит держит не песочница, не ACL и не Chrome (в `tasklist` ни одного chrome/crashpad):
  похоже на внешний фильтр (антивирус). Копать дальше не стал — 11 папок это ~350 МБ.
- Промежуточная гипотеза «корзина заполнена» **проверена и отброшена**: файл на 1 МБ уходит в корзину,

- Свой контроль был пустым: `echo x > Default/probe.txt` падал сам, а я читал это как «файл удалился».

## Состояние профиля: файлами не сбросить — только через chrome.storage

Хозяин почистил temp сам, но наборы после этого стали падать: в `test-popup` пять проверок «по
умолчанию» видели настройки **прошлого** прогона (галочка приписки включена, в поле чужой текст
«Свой текст приписки для проверки.»), в `test-format` mock6 не запускалась отмена.

Разбор по шагам — каждый шаг сначала проверялся, а не угадывался:

1. `freshProfile` чистил `Default/Sync Extension Settings` и `Default/Local Extension Settings`. Сообщений
   «не смог очистить состояние профиля» в логе не было, и это сбивало: решил, что чистка проходит.
   **Ловушка:** `run-suite.sh` печатает только строки по фильтру (`PASS|FAIL|всего проверок|тост|…`),
   а stderr харнесса туда не попадает. «В логе нет ошибки» ≠ «ошибки не было».
2. Прямой опыт: вызвал `PATHS.freshProfile("popup")` руками — EPERM на
   `.../Sync Extension Settings/<id>/000003.log`. Повторы `maxRetries: 20, retryDelay: 250` не спасают.
3. Проверил, не песочница ли: тот же вызов **без изоляции** — тот же EPERM. И не ACL: `icacls` показывает
   полный доступ для obogr (наследуется), а `icacls /grant obogr:(F) /t` не может обработать 934 файла
   из 1092. Chrome не запущен (в `tasklist` ни одного chrome/crashpad). Держит что-то внешнее.
4. Перебрал все файлы в обоих каталогах поштучно: не отдаётся **ни один** — ни `000003.log`, ни пустой
   `LOCK`, ни `MANIFEST`. Обрезать до нуля тоже нельзя (EPERM). Значит состояние профиля файловыми
   операциями неустранимо.
5. Гипотезу «помогает переименование» проверил дважды: один раз папка после переименования удалилась,
   второй раз само переименование упало с EPERM. Приём ненадёжный — как основа не годится.
6. Отброшенные по дороге версии: «корзина заполнена» (файл на 1 МБ уходит в корзину, `C:\$Recycle.Bin`
   занимает 19 МБ), «профиль держит Chrome» (процессов нет), «виновата песочница» (EPERM и без неё).

**Решение — чистить через сам `chrome.storage`, в копии расширения.** `PATHS.stubStorageReset(TEST_EXT)`
вставляет в `background.js` копии сброс `sync` + `local`, который срабатывает один раз за прогон: флаг
лежит в `chrome.storage.session`, а оно исчезает вместе с браузером. Иначе service worker перезапустится
посреди набора и сотрёт то, что набор только что сохранил (наборы проверяют, что правки переживают
перезагрузку страницы). Правку вносим в копию, а не в продукт: `copyDir` идёт перед ней, поэтому на
следующем прогоне файл снова чистый — тот же приём, что с подменой внешних API.

Заодно выяснилось, почему прогоны распухли до 13–22 минут: `freshProfile` тратил на каждом наборе до
десяти секунд (20 повторов × 250 мс × два каталога) на удаление, которое всё равно не проходило.
Теперь `PATHS.testProfile(tag)` — просто путь, без чистки.

Правки: `test/paths.cjs` (`freshProfile` → `testProfile` + `clearStorage`), 14 наборов (вызов
`PATHS.clearStorage(c, extId)` сразу после `Extensions.loadUnpacked`), `tools/clean-profiles.cjs`
(список постоянных имён теперь парсит `testProfile`).

**Первая попытка была неверной, и это стоит помнить.** Я вставил сброс в `background.js` **копии**
расширения — тем же приёмом, что и подмена внешних API. Набор попапа как шёл с пятью провалами, так и
пошёл. Причина: **service worker у наборов не запускается вообще**. Попап открывают как обычную страницу
`chrome-extension://<id>/popup.html`, она читает `chrome.storage` напрямую, фоновых сообщений нет —
значит вставка не выполнялась ни разу. Подтвердил по профилю: `Default/Service Worker/Database` остался
от прошлого прогона, а `Default/Extension Scripts` обновился. Урок общий: **механизм, который «должен
срабатывать», надо проверять по признаку, что он сработал**, иначе он просто тихо ничего не делает.

Рабочее решение — снаружи: `PATHS.clearStorage(c, extId)` открывает страницу расширения и зовёт
`sync.clear()` + `local.clear()`, а если не вышло — падает. Проверка на одном наборе: `test-popup`
86/0 и 42 секунды вместо ~2 минут.

Отброшенные варианты, чтобы не возвращаться: сброс в `popup.js` (попап заполняет поля из хранилища при
загрузке, а `chrome.storage` асинхронный — гонка), сброс в `content.js` (в контент-скрипте нет
`chrome.storage.session`, а чистить на каждой загрузке нельзя: наборы проверяют, что правки переживают
перезагрузку), «флаг в sessionStorage страницы» (слетит при открытии второго таба).
